Shared memory & skills for AI teams

One memory. One skill set. Every AI tool.

Capture a thought in one project — a decision, a preference, running context — and recall it weeks later, from a different repo, session, or a teammate's AI client entirely. Skills work the same way: write a working practice once, and every tool your team or enterprise org runs — Claude Code, Claude Desktop, or anything else speaking MCP — pulls the same version.

01The problem

Your AI sessions don't remember each other.

Every AI coding session starts scoped to a working directory. Decisions made Monday in one repo are invisible Thursday in another — even to the same person, even in the same team.

↺

Repo-scoped memory

Context a session builds up lives and dies with that session. Move to a different project and you're explaining the same decisions again.

👤

Individual heroics

Whoever set up a working practice first becomes the single point of knowledge for it. It doesn't travel to a teammate, or to a different AI tool.

⧉

Vendor silos

Standardize on one AI harness and every other one falls behind — or you hand-copy the same instructions into each tool's own format.

02How it works

Contexts are the unit of memory.

Every thought lives inside a context — an opaque id, not a name you can guess. A context belongs to one organization and is either open to every member, or restricted to an explicit grant. Every person also gets one private personal context automatically.

01

List your contexts

list_contexts() returns every context you can access — id, name, and description. It's the only way to get a valid context id; there's no default and no way to guess one.

02

Capture and recall

capture_thought saves a note. search_thoughts finds it again by meaning, not just keywords — embedded with Vertex AI's gemini-embedding-001. browse_recent and view_stats round out day-to-day use.

03

Org membership gates access

Every context belongs to an org. org-visibility contexts are open to every member automatically; restricted ones need an explicit grant. Owners and admins manage both.

04The tool surface

Everything a session can call, in one table.

06Security & tenancy

Federated sign-in. Row-level isolation. No shared secrets.

  • Federated OIDC sign-in. Google, Okta, Microsoft Entra, or a self-hosted identity provider — any standards-compliant issuer works via .well-known/openid-configuration discovery.
  • Our own OAuth 2.1 authorization server. Dynamic client registration and the standard authorization-code + PKCE flow, minting RS256-signed JWTs as the access/refresh tokens clients actually use.
  • Postgres + pgvector, row-level tenancy. Every context and thought carries an org_id; access checks run on every call.
  • Data residency. europe-west1, us-central1, asia-northeast1 — set per organization at creation.

Sign up via MCP

Create your organization straight from the terminal.

There's no web signup form. Two HTTP calls create and verify your org; everything after that — including upgrading your plan — is a real MCP tool call.

bootstrap — plain HTTP, not MCP
// 1. Create your organization (free Individual plan by default)
curl https://mcp.integratedai.co.uk/v1/organizations \
  -d '{"name":"Acme Inc","contact_email":"you@acme.com"}'
// → {"org_id": "…", "status": "pending_verification"}

// 2. Check your email for a code, then verify
curl https://mcp.integratedai.co.uk/v1/organizations/<org_id>/verify \
  -d '{"code":"123456"}'
// → {"status": "active", "plan_id": "individual", "api_key": "sk_live_…"}

Put that api_key into your MCP client config as a bearer token, and you're live:

~/.claude.json
{
  "mcpServers": {
    "integrated-ai": {
      "type": "http",
      "url": "https://mcp.integratedai.co.uk/mcp",
      "headers": { "Authorization": "Bearer <api_key>" }
    }
  }
}
